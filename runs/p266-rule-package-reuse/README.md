# p266 — 跨版本复用：真正要重做的是桥，不是规则

日期：2026-11-04。加一个目标版本（1.21.1 → 1.21.4）时，规则要不要全部重写？
本回合用两个可量化的测量回答：**不用重写规则，但要重编桥。**

## 1. 目标稳定性：规则里点名的成员还在不在

用 p261 的检查器把两个规则包各对着两个 stub 跑一遍：

| 规则包 | vs 1.21.1 stub | vs 1.21.4 stub |
|---|---:|---:|
| `fabric-1.21.1`（29 文件 / 119 条） | 4 missing | **4 missing** |
| `fabric-1.21.4`（6 文件 / 11 条） | 2 missing | 0 missing |

**关键在第二列**：1.21.1 的规则对着 1.21.4 跑，缺失数和对着自己跑**一模一样**——说明那 4 个不是版本漂移，
而是 **Balm 的类**（模组依赖，本来就不在 Minecraft stub 里）。

于是：**1.21.1 规则点名的每一个 Minecraft 成员，在 1.21.4 里都还在。**

反向不成立（1.21.4 → 1.21.1 有 2 个缺失），也符合预期：新规则用到了 1.21.4 才有的东西
（`method_46765` 等）。

## 2. 桥依赖：真正的工作量在哪

| 规则包 | 需要桥 | 免桥 |
|---|---:|---:|
| `fabric-1.21.1` | **91** | 28 |
| `fabric-1.21.4` | 10 | 1 |

1.21.1 的 119 条里 **91 条会调用桥**。桥是对着 Minecraft 类写的 Java 源码，
换目标就要**重编**（签名可能变）；而免桥的 28 条是纯文本改写
（`methodRenames` 2、`mixinClassReplacements` 11、`mixinConfigAdditions` 10、`mixinStrips` 1、
`signatureAdaptations` 2、`mixinCallbackAdaptations` 2），可以跨版本直接搬。

所以迁移成本的结构是：

```
迁移一个目标 ≈ 规则文本基本不动（target 100% 稳定）
            + 重编 91 个桥（按新目标的类签名）
            + 为新版本新增的破坏补规则（这次是 11 条）
```

## 3. 一个重要警告

**"目标成员还在"不等于"这条规则在这个版本上仍然是对的"。**
1.21.1 的某条改名规则，是因为 1.21.1 改了签名才需要；到 1.21.4 可能多余、甚至有害
（比如把已经正确的调用再改一次）。

本回合量的是**复用成本**，不是**正确性**。要判断正确性，还得逐条回到"该模组在这个目标上
有没有坏"的证据（p250 那种分类）。

## 4. 结论

- 规则包**不需要按目标重写**，intermediary 名跨版本足够稳定。
- 桥是主要成本项，且 91/119 的规则依赖桥 → **桥的编写质量决定了迁移成本**。
- 这条结论支持当前设计（`TargetProfile` + 每目标规则包 + 每目标桥目录），并说明为什么
  `rules/fabric-1.21.4` 只有 6 个文件却要覆盖 1.21.1 的 119 条：**大部分内容不需要新规则。**

## 5. 边界

- 静态比较，没有 patch、没有运行。
- 只比了 target 层面的存在性，没有比对语义（见第 3 节）。
- 两个 stub 都是 intermediary 名；如果哪天跨到非 intermediary 命名空间，这个结论要重做。
