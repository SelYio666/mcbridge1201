# p270 — 1.21.1 规则包审计：没有历史遗留

日期：2026-11-04。p266 说"1.21.1 的 29 个规则文件、119 条规则，target 层面 100% 稳定"，
那有没有需要清理的历史遗留？本回合审计后结论是：**没有**；但审计工具本身修了两次误报，那两次
比结论更有信息量。

## 1. 审计的三个维度

| 维度 | 含义 |
|---|---|
| 无 `id` | 无法被证据引用、无法被 `applied` 统计的规则 |
| 无说明 | 以后没法重新判定，只能"信"或"删" |
| 孤儿 | 从未在任何 `runs/` 文件里出现过 |

## 2. 两次误报，都是"判据太窄"

**（一）孤儿：47 → 0。**
第一版只查"规则 id 是否出现在 `runs/` 的文本里"。可是**批量规则是按文件记录证据的**——
`container.json` 的 12 条规则，证据里写的是"container.json"或那次 run，不是每条 id。
改成"id 或文件名任一被提及"之后，47 条孤儿全部归零。

**（二）无说明：6 → 0。**
第一版只查 `evidence` 字段是否够长。但**不同规则类型把说明放在不同字段**：

- `immediatelyfast` 的 5 条：`evidence` 只有一句 `runs/p175-map-atlas`，真正的技术说明在
  `risk` 里（例如"1.21.1 method_32601 改成收 class_9209，原始 int 签名在 apply 阶段被拒"）；
- `lithium` 的 1 条 `mixinStrips`：schema 里根本没有 `evidence`，说明在 `reason` 里
  （"Redirector 扫到 0 个目标，1.21.1 服务端启动时 InjectionError"）。

改成"按规则类型取 evidence / risk / reason / why / value 里最长的那段"之后，归零。

**这两次误报的形状和 p267 是同一个**：不是数据有问题，是**判据比现实窄**，于是把"另一种写法"
当成"缺失"。

## 3. 结论

```
rules/fabric-1.21.1: 119 rules in 29 files
  kinds: 12 种（methodRedirects 54、mixinClassReplacements 11、constructorRedirects 11 …）
  capabilities: 89 distinct，14 个被多条规则共用（最多的是 mixin-class-replacement 9 条）
  无 id：0    无说明：0    孤儿：0
```

**1.21.1 的规则包不需要清理。** 每条规则都带 id、都带说明、都被证据提到过。

## 4. 留下的东西

`tools/audit_rule_package.py`——只读，不改规则。以后每加一批规则都可以跑一次，防止出现
"加完就没人记得为什么"的条目。

## 5. 边界

- 只检查"有没有说明"，**不检查说明是否仍然正确**。
- capability 重复不是错误：一个桥一条规则是正常粒度；报告只是列出来，供人判断。
- 对 1.21.4 的 6 个文件没有跑（数量太小，没有审计价值）；工具本身通用。
