# p265 — key 注入的离线边界：行为做不到，结构可以

日期：2026-11-04。上一轮说"用动态代理造假 Registry 就能断言 key 真的注入了"。
**这个计划失败了一半**，本回合把边界探清楚，并把能做到的那部分做成检查。

## 1. 为什么行为验证做不到

`Registry`（`class_2378`）是接口，动态代理确实造得出来；`RegistryKey` 也能用
`class_5321.method_29180` 正常构造。卡在最后一步：

```
class_1793.<init>  →  class_9334.<clinit>  →  ExceptionInInitializerError
```

`Item.Settings` 的构造器会触碰 **数据组件注册表**（`class_9334`），它需要运行中的游戏才能初始化。

所以「Settings 对象上真的挂到了正确的 RegistryKey」这条断言**离线无法成立**。
写好的 `RegistryKeyInjectionTest` 已删除——留一个 `@Disabled` 的测试只会让人以为它跑过。

## 2. 能做到的：结构断言（5 项全过）

反汇编 `RegistryKeyContext` 并断言它做了该做的事：

| 检查 | 结果 |
|---|---|
| `settings()` 派生出 key（读 `method_46765` + `method_29179`） | 通过 |
| `settings()` 真的把 key 设上去（`method_63686`） | 通过 |
| 调用顺序 | `method_46765` → `method_29179` → `method_63686` |
| 有上下文守卫（`ifnull` 分支） | 通过 |
| `getWithKey` 的恢复在异常表里（finally，不是直线清空） | 通过 |

这几条能挡住"桥被改坏"的多数情形：少一步、顺序颠倒、丢了守卫、把 finally 写成直线清空。
